# V5.30 — Low-Temperature Markets Build Spec

Status: **data source RESOLVED** (2026-06-26). Build gated on V5.29.D highs validation; start ~6/29.
Market: Kalshi `KXLOWT{CITY}-{YYMMMDD}` (daily calendar-day minimum temperature).

---

## 1. Data source (resolved)

Two questions decided the architecture. Q1 is answered and is the one that mattered.

**Q1 — Can wethr reconstruct the settlement min? YES.**
The calendar-day minimum of wethr's raw observation history matches the Iowa CLI
settlement min to **avg 0.32°F, worst 0.8°F across 12 city-days** (Miami, New Orleans,
LA, Houston, Phoenix, Chicago; 6/24–6/25). This means lows have a source that is both:

- **Settleable** — Iowa CLI (`cli.py` JSON, `entry['low']`). Ground truth, unaffected by the wethr outage.
- **Intraday-trackable** — wethr obs-history min converges to the settlement value in real time (~0.3°F).

That unlocks the same "bet the certainty curve" play as afternoon highs: watch the
calendar-day min form, fire when it locks. No need to wait for CLI to post.

**Q2 — Is forecast low the calendar-day min or the upcoming overnight low? OPEN, non-blocking.**
Forecast `low` drifts within a day (Vegas 84→91 same date), suggesting it predicts the
upcoming overnight low, not the already-occurred calendar-day min. This does NOT affect
sourcing — since Q1 is YES, forecast low is only a *predictor input*, never the settlement
target. Resolve during modeling, not before.

## 2. wethr obs-history — how to call it

Endpoint: `https://wethr.net/api/v2/observations.php`, mode param **omitted** = history.

- **Requires** `start_time` + `end_time` (UTC, ISO `YYYY-MM-DDTHH:MM:SSZ`).
- **Range cap:** wide windows return `{"error":"Range too large."}`. 84h failed.
  → Fetch in **per-UTC-day ≤24h chunks and merge.** Pull ~4 UTC days back to fully cover
  the last 2 *local* calendar days (a US local day spans 2 adjacent UTC days).
- Returns a LIST of ~970 records/city over 4 days (dense enough to trust the min).

**Real obs schema:** `id`, `station_code`, `observation_time`, `temperature`,
`six_hour_high`, `six_hour_low`, `twentyfour_hour_high`, `twentyfour_hour_low`.

> **Reconstruct the min off the raw `temperature` series** — that's what gave the 0.32°F
> match. **Do NOT trust the precomputed `_low` fields** (`six_hour_low`,
> `twentyfour_hour_low`); they returned None in `latest` mode and are not the calendar-day min.

**Min reconstruction:** group records by **local** calendar date
(`observation_time` → city tz), take `min(temperature)` per date.

## 3. City allowlist (low-side)

Low-side volatility tiering is the **OPPOSITE of highs**: coastal/humid = tight lows,
desert = wide lows.

- **Allowlist leads (tight):** Miami, New Orleans, Los Angeles, Houston.
- **Avoid early (wide lows):** Phoenix, Las Vegas — desert diurnal swing is large on the low side.
- LA stays on the allowlist. The `CLI=None` seen 6/25 was a transient reporting lag, not a
  station gap (came back 61/62 next run). Still: keep a LOUD flag if LA CLI is null on a
  settled day — don't bet a city whose settlement value you can't read.

## 5. Build order (when unfrozen)

1. `fetch_lows.py` foundation already exists: `fetch_kalshi_low_brackets()`,
   `fetch_nws_low()`, `fetch_cli_min_temp()`. **Never touches `fetch_weather.py`.**
2. Add obs-history min reconstruction (chunked fetch + local-day grouping, per §2).
3. Build consensus/sigma/bracket logic on confirmed fields. Reuse highs sigma-CDF
   structure but **recalibrate BASE_SIGMA per city on low-side data** (tiering is inverted).
4. Set cron windows **last** — only after observed-min timing is characterized.
   Do NOT guess windows; that recreates the silent-misalignment risk.
